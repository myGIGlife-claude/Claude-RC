# In-app Migrate: design

Settings › Connection › **Migrate**: move everything from one cLaudeRC server to another, from the phone.
Both servers must already be in the app (host, user, host key trusted; the phone key authorized on both).
Everything below is the contract between the app, the server actions and `claude-backup`.

## Flow (the wizard's steps)

1. **Choose**: dropdown *From* and dropdown *To* (the app's server list; they must differ), and the **user name** to run Claude as
   on the new server (default `claude`). If the *To* entry's user already equals that name nothing is created.
2. **Check** (`migrate-plan` on From): sessions with `busy`/`waiting`, repos whose work exists only there, Claude logins
   (main + workers), connected services, docker volumes, estimated size. The user sees it before anything happens.
3. **Stop sessions**: idle sessions are stopped automatically (`stop`). A session that is `busy` or `waiting` is listed
   and the user decides per session: *wait* (re-check) or *stop anyway*. Nothing proceeds while a session is running.
4. **Sudo check, then create the user on To** (only if it doesn't exist): `migrate-create-user` with the sudo password (needs `ALLOW_RUN=1`
   on that server, like Run a command). It creates the Linux user, installs Claude Code and the cLaudeRC scripts for it
   and authorizes the phone key. The app then adds a server entry *To (as <user>)* with the same host and pinned host key.
5. **Transfer**: `migrate-keygen` (From) -> `migrate-authorize` (To) -> `migrate-send` (From, detached) streams an encrypted
   `claude-backup` over SSH into the To user's `~/backups/`; the app polls `migrate-status`. Claude logins are NOT copied
   (`--no-claude-login`): two servers refreshing one login would sign each other out.
6. **Restore** (`migrate-restore` on To, detached, the passphrase goes phone -> To on stdin, never shown): runs
   `claude-backup import --clone`; the app polls `migrate-status`.
7. **Sign in on To**: the app's normal Claude sign-in for the main account and for each worker, against the To server.
8. **Sign out on From** (the user ticks what): `migrate-signout-old`: deletes the local Claude logins (no revoke call), removes
   the GitHub token, stops autostart from resurrecting sessions. Optional per item.
9. **Reboot** (optional, `migrate-reboot`, sudo password): the app waits for the server and reconnects.
10. **Verify** (`migrate-verify` on To): a checklist; the wizard ends with "100% done" only when every item is ok, otherwise it shows
    exactly what is missing.

## Server actions (SCRIPT_API 34)

All answer the usual `{"ok":true,"data":...}` / `{"ok":false,"error":{code,message}}`. Long jobs are detached; state lives in
`~/.local/state/claude-launcher/migrate/status.json` (mode 600) and is read with `migrate-status`.
`migrate-sudo-check`, `migrate-create-user`, `migrate-reboot`, `migrate-send` and `migrate-passphrase` need `ALLOW_RUN=1` on the server they run on
(`run_disabled` otherwise, with the line to add to `~/.config/claude-launcher/config`). The sudo ones read the sudo password from the first stdin line
(empty when `migrate-sudo-check` says `root` or `nopasswd`: the wizard only asks for a password when the mode is `password_needed`, and explains the options when it is `none`).
So set `ALLOW_RUN=1` on BOTH servers before starting the wizard.

| action | on | args / stdin | data |
| --- | --- | --- | --- |
| `migrate-plan` | From | none | `{sessions:[{name,busy,waiting}], repos:[{dir,state,rescued,skipped_reason}], logins:{claude:bool,workers:[names]}, services:[ids], docker_volumes:[..], estimate_mb:int, other_dirs:[..]}` |
| `migrate-keygen` | From | none | `{public_key:"ssh-ed25519 AAAA… clauderc-migrate"}` (ephemeral key in `~/.config/claude-launcher/migrate/`) |
| `migrate-authorize` | To | stdin line 1: the public key line; line 2 (optional): the From server's address | `{authorized:true}` appends `restrict,command="<home>/.local/bin/claude-backup receive"[,from="addr"] <key>` to `~/.ssh/authorized_keys` (marker comment `clauderc-migrate`); `from=` is added only when the address is a literal IPv4/IPv6 address (sshd compares it with the client IP and doesn't resolve names), never for a host name; the file is rebuilt in a temp file (old content copied first) and moved over, and an unreadable file aborts without touching it |
| `migrate-send` | From | stdin: line 1 host, 2 port, 3 user, 4 host-key type, 5 host-key base64 blob (the To server, as pinned in the app) | `{started:true}`; detached: `claude-backup export --no-claude-login` with a generated passphrase file, then `ssh -i <migrate key> … < file` into `receive` (host key pinned from the five lines, no other host accepted) |
| `migrate-passphrase` | From | none | `{passphrase:"XXXX-…"}` (the one generated by `migrate-send`; `not_ready` until the export started) |
| `migrate-status` | any | none | `{job:"send"\|"restore"\|"none", phase:"export"\|"transfer"\|"restore"\|"done"\|"failed", message, pct:0-100, bytes, file:"incoming-….gpg" (on To), started, updated, error}` |
| `migrate-restore` | To | stdin line 1: passphrase; arg: the incoming file name (from `migrate-status`) | `{started:true}`; detached `claude-backup import FILE --pass-file <tmp> --clone`, deletes the file and the pass file when done |
| `migrate-sudo-check` | To | optional stdin line 1: a sudo password to test | `{mode:"root"\|"nopasswd"\|"password_ok"\|"password_needed"\|"none"}`: `root` = the SSH user is root (no sudo at all); `nopasswd` = `sudo -n true` works (leave the password empty); `password_ok` = the given password works; `password_needed` = sudo exists but needs a (correct) password; `none` = this user can't use sudo |
| `migrate-create-user` | To | arg `<name>` (`^[a-z][a-z0-9_-]{0,30}$`); stdin: sudo password, then the phone's public key line | `{created:true, home, autostart_pending}`; refuses reserved names (`root`, `admin`, `sudo`, `wheel`, `adm`, `staff`, `docker`, system accounts); right after `adduser` it writes `~/.clauderc-migrate-user` as root (mode 644) and runs `sudo -l -U NAME`: any sudo rule for the new user deletes it again (`userdel -r`) and fails with `sudo_rule`. An existing user is reused only if that root-owned marker is there; the docker group is joined only by a user this run created |
| `migrate-verify` | To | arg: the manifest file name of the restore (or none) | `{items:[{id,ok,detail}], ok:bool}`: scripts installed and SCRIPT_API current, `~/.claude` and `~/.config/claude-launcher` present with mode 700, `env` mode 600, worker folders, every repo of the manifest present, project git remotes reachable, `claude`/`gh` runnable, autostart installed, pending signs-in listed (not an error) |
| `migrate-signout-old` | From | args: any of `claude`,`workers`,`github`,`autostart` | `{done:[…]}`; whatever is ticked, it also deletes the transfer key folder (`~/.config/claude-launcher/migrate`), the passphrase files and `~/backups/migrate-*.gpg` |
| `migrate-reboot` | To | stdin: sudo password | `{rebooting:true}`; `busy` while a migrate job is running |

The incoming file name is `incoming-YYYYmmdd-HHMMSS.gpg`, or `incoming-YYYYmmdd-HHMMSS-N.gpg` (N 1-999) when `receive` had to avoid a name clash.
The restore's passphrase file lives in `~/.local/state/claude-launcher/migrate/` (`restore-pass.XXXXXX`, mode 600), never in the config folder.

`claude-backup import` never restores `~/.ssh/authorized_keys` (unless `--with-authorized-keys`, for a same-user move by hand),
`~/.config/claude-launcher/config` (the new server keeps its own; only `PROJECTS_DIR` is taken when it sets none) or
`~/.config/claude-launcher/migrate`; `export` never stores the migrate folder.

`claude-backup` additions: `plan --json` (what export would do, no archive), `export --no-claude-login` (leaves out every
`.credentials.json`: the main one and the workers'), `receive` (reads one stream on stdin into `~/backups/incoming-<time>.gpg`,
mode 600, refuses more than 20 GB, prints the file name), `import --manifest-out FILE` (writes the manifest it restored so
`migrate-verify` can compare).

## Rules

- Nothing is deleted on the From server except by `migrate-signout-old`, and only what the user ticked.
- The phone only relays: the passphrase and the sudo password are held in memory for the wizard and sent on stdin.
- The ephemeral migrate key can only run `claude-backup receive`, is removed from `authorized_keys` by `migrate-verify` once the
  restore is done, and the private half is deleted by `migrate-signout-old`.
- A failed step leaves everything restartable: `migrate-status` says where it stopped, retry resumes at that step.
